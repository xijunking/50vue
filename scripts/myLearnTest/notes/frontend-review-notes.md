# 前端相关知识复习笔记

这份笔记整理了前面聊过的前端相关内容，重点是把这些零散概念串成一条线，方便后续复习时按“数据怎么流转、任务怎么执行、界面怎么更新”的思路来理解。

---

## 1. 一条总线：前端代码到底在干什么

无论是 Web、Vue、React，还是 RN、uni-app，很多问题都可以放进这条总线上理解：

1. 数据从哪里来
2. 数据存在哪里
3. 谁会使用它
4. 什么时候更新
5. 更新后谁来响应
6. 最终怎么反映到界面上

如果把这条线理顺，`Promise`、`async/await`、状态管理、生命周期、缓存这些概念就不容易散。

---

## 2. JavaScript 执行顺序：同步、微任务、宏任务

### 2.1 核心结论

JavaScript 主线程一次只做一件事，常见顺序可以先记成：

`同步代码 > 微任务 > 宏任务`

### 2.2 三类任务

#### 同步代码

会立刻从上到下执行，例如：

- 普通函数调用
- `console.log()`
- `new Promise()` 里的 executor

#### 微任务

会在当前同步代码执行完后立刻清空，例如：

- `Promise.then()`
- `Promise.catch()`
- `Promise.finally()`
- `await` 后面的续执行代码

#### 宏任务

会在微任务清空后，进入下一轮事件循环，例如：

- `setTimeout()`
- `setInterval()`
- DOM 事件
- 一些 I/O 回调

### 2.3 最小记忆版

先背这 4 句：

1. 普通代码先同步执行
2. `new Promise()` 里的函数也是同步执行
3. `.then()` 和 `await` 后续代码是微任务
4. `setTimeout()` 是宏任务

## 3. `new Promise()`、`Promise.resolve()`、`.then()` 的区别

### 3.1 `new Promise(executor)`

`Promise` 是构造函数，`new Promise(executor)` 中的 `executor` 会立刻同步执行。

```js
new Promise((resolve) => {
  console.log('这里是同步执行的')
  resolve()
})
```

要点：

- `new Promise()` 本身不是“自动异步”
- 真正进入微任务的是后面的 `.then()`

### 3.2 `promise.then(callback)`

`.then()` 不是立刻执行回调，而是把回调注册成微任务，等当前同步代码结束后执行。

```js
Promise.resolve().then(() => {
  console.log('这是微任务')
})
```

### 3.3 `Promise.resolve(value)`

`Promise.resolve(value)` 的意思是：返回一个状态已经完成的 Promise，结果值是 `value`。

如果 `value` 是函数，那只是“把函数当普通值包起来”，不会自动执行这个函数。

```js
Promise.resolve(() => {
  console.log('不会自动执行')
})
```

上面这段代码不会打印任何东西，因为传进去的是函数本身，不是函数调用。

如果想让它进入微任务执行，应该写：

```js
Promise.resolve().then(() => {
  console.log('会在微任务里执行')
})
```

## 4. `Promise` 和 `async/await` 的关系

### 4.1 本质关系

`async/await` 不是另一套异步机制，它是基于 `Promise` 的语法糖。

可以先记成：

- `Promise` 是底层对象和链式写法
- `async/await` 是更像同步代码的写法

### 4.2 `async` 做了什么

`async` 加在函数前，表示这个函数返回的一定是 Promise。

```js
async function test() {
  return 123
}
```

上面返回的本质上相当于：

```js
function test() {
  return Promise.resolve(123)
}
```

### 4.3 `await` 做了什么

`await` 的含义可以理解成：

“先暂停当前 `async` 函数后面的逻辑，等右边 Promise 有结果后，再继续执行。”

但注意：

- `await` 不会阻塞整个 JS 主线程
- 它只是暂停当前函数后续逻辑
- `await` 后面的代码，本质上也是微任务续执行

### 4.4 对比写法

```js
fetchData()
  .then((res) => {
    console.log(res)
  })
  .catch((err) => {
    console.log(err)
  })
```

```js
async function run() {
  try {
    const res = await fetchData()
    console.log(res)
  } catch (err) {
    console.log(err)
  }
}
```

它们本质上是同一类事情，只是表达方式不同。

## 5. 原生 JavaScript 里的异步数据流

### 5.1 等待接口数据，到底发生了什么

请求接口时，JS 不是“傻等在那里不动”，而是：

1. 发起请求
2. 先继续执行其他同步代码
3. 请求完成后，把后续处理逻辑放回任务队列
4. 等主线程空闲时再继续处理

例如：

```js
fetch('/api/user')
  .then((res) => res.json())
  .then((data) => {
    console.log('拿到数据了', data)
  })
```

本质是：

“先登记后续逻辑，等结果回来再继续。”

### 5.2 原生 JS 更新界面

在原生 JS 里，拿到数据后通常是手动改 DOM：

```js
fetch('/api/user')
  .then((res) => res.json())
  .then((data) => {
    document.getElementById('name').textContent = data.name
  })
```

这可以理解为：

`请求数据 -> 拿到结果 -> 手动更新局部 DOM`

## 6. Vue / React 的共同思路：状态驱动视图

### 6.1 核心链路

Vue 和 React 通常不是“拿到数据后直接操作 DOM”，而是：

`请求数据 -> 更新状态 -> 框架根据状态变化更新视图`

### 6.2 Vue 的思路

Vue 更强调响应式：

- 修改 `ref` / `reactive`
- Vue 追踪依赖
- 只更新依赖该数据的界面部分

可以先记成：

`响应式数据变了 -> 模板重新计算 -> DOM 局部更新`

### 6.3 React 的思路

React 更强调状态变化后重新渲染：

- 调用 `setState`
- 组件重新执行
- 生成新的虚拟 DOM
- 对比差异
- 更新真实 DOM

可以先记成：

`state 变了 -> 组件重新渲染 -> diff -> DOM 局部更新`

### 6.4 最小结论

原生 JS：

`请求回来 -> 手动改 DOM`

Vue / React：

`请求回来 -> 改状态 -> 框架帮你改 DOM`

## 7. 状态管理：局部状态、全局状态、派生状态

### 7.1 一个核心判断标准

不要先问“这个状态重不重要”，而要先问：

`谁需要这份数据？`

### 7.2 局部状态

只在当前组件或当前页面的小范围内使用。

常见例子：

- 弹窗开关
- 输入框内容
- loading 状态
- 当前 tab
- 表单错误提示

特点：

- 生命周期短
- 影响范围小
- 离组件越近越合适

### 7.3 全局状态

需要跨页面、跨组件、多层级共享。

常见例子：

- 当前登录用户
- 权限信息
- 当前租户 / 当前项目
- 主题模式
- 购物车数量

特点：

- 多处共享
- 生命周期长
- 常常和业务上下文绑定

### 7.4 派生状态

由其他状态计算出来，不应该重复存储。

常见例子：

- 提交按钮是否可点击
- 列表过滤结果
- 总价
- 是否显示空态

原则：

`能计算出来的，尽量不要重复存`

否则容易出现两份状态不一致。

## 8. 初始化、持久化、更新时机

### 8.1 初始化：状态最初从哪来

常见来源：

1. 默认值
2. 接口返回值
3. 路由参数 / 父组件传参
4. 本地持久化存储

### 8.2 持久化：刷新后还要不要在

#### 不需要持久化

- 弹窗开关
- hover 状态
- 临时 loading
- 当前一次输入中的中间值

#### 需要持久化

- 登录凭证
- 主题偏好
- 用户语言
- 草稿内容
- 上次筛选条件

### 8.3 更新时机

常见更新时机有 4 类：

1. 用户操作触发
2. 接口返回触发
3. 外部上下文变化触发
4. 由已有状态派生重算

---

## 9. 服务端状态和本地状态

工作里经常容易把所有数据都混在一起，实际上至少可以先粗分成两类。

### 9.1 服务端状态

来自接口、数据库、后端系统。

例如：

- 用户详情
- 列表数据
- 订单信息

这类数据更关注：

- 拉取
- 刷新
- 缓存
- 失效
- 重试

### 9.2 本地 UI 状态

只服务于当前页面和交互。

例如：

- loading
- 当前选中项
- 弹窗是否打开
- 表单输入过程中的状态

这类状态更关注：

- 组件边界
- 交互体验
- 生命周期

---

## 10. 一个实用的状态判断框架

以后遇到一份数据，可以先问自己这 5 个问题：

1. 谁需要它
2. 它从哪来
3. 刷新后还要不要保留
4. 它是原始状态还是可以计算出来
5. 谁来更新它、什么时候更新

这 5 个问题能帮助判断：

- 是局部还是全局
- 是暂存还是持久化
- 是服务端状态还是本地状态
- 要不要单独存

---

## 11. Web、客户端、系统层的认知差别

### 11.1 Web 更关注什么

Web 开发通常更关注：

- 页面状态
- 异步请求
- 渲染更新
- DOM / 组件更新

### 11.2 客户端更关注什么

客户端不是推翻 Web 思路，而是在原有基础上多了更多系统边界。

除了状态和视图，还要多考虑：

- 生命周期
- 线程
- 本地缓存
- 文件系统
- 系统权限
- 蓝牙、定位、相机等系统能力
- 页面前后台切换

### 11.3 更往下的系统 / 硬件层

再往下会涉及：

- 进程
- 线程
- 内存
- 调度
- 驱动
- 中断
- 总线

越往下层，越关注“执行机制”和“资源管理”；越往上层，越关注“业务语义”和“用户交互”。

## 12. RN / uni-app 场景下的线程认知

### 12.1 先分清：异步不等于线程

`Promise`、`async/await`、回调，描述的是：

`任务什么时候继续`

线程描述的是：

`任务到底在哪条执行线上跑`

所以：

- 异步 != 多线程
- `await` != 自动开新线程

### 12.2 客户端里最重要的线程分工

可以先用一个简化模型理解：

#### UI 线程

负责：

- 界面绘制
- 点击响应
- 动画
- 页面切换

原则：

`不要把耗时工作放在 UI 线程`

#### JS 逻辑线程

负责：

- 组件逻辑
- 状态更新
- 生命周期回调
- Promise / async/await 的后续逻辑

#### Native / 后台线程

负责：

- 网络请求
- 文件读写
- 蓝牙通信
- 数据库操作
- 其他系统能力

### 12.3 为什么会卡顿

常见原因不是“接口慢”这么简单，而是某条关键线程被堵住了。

例如：

- JS 做了大量同步计算
- 页面触发了过多状态更新
- 主线程做了重任务
- 蓝牙 / 文件 / 图片处理链路过重

### 12.4 蓝牙打印这类系统 API 的理解方式

以蓝牙打印为例，粗略流程可能是：

1. 页面点击打印
2. JS 层组装打印数据
3. 调原生蓝牙 API
4. 系统蓝牙服务处理通信
5. 打印机接收数据
6. 结果回调给应用
7. 页面根据结果更新状态

所以表面上你写的是几段 JS，底层其实已经跨了：

- JS 逻辑层
- Native 层
- 系统蓝牙能力
- UI 更新链路

### 12.5 对当前 RN / uni-app 开发最实用的结论

先掌握这几件事就够用了：

1. UI 线程不能做重活
2. JS 异步不等于多线程
3. 系统 API 往往不在 JS 线程里真正执行
4. 结果回来时要注意生命周期是否还安全
5. 卡顿、延迟、回调晚，很多时候和线程调度有关

## 13. 生命周期和缓存，为什么在客户端更重要

### 13.1 生命周期

在客户端里，生命周期比 Web 更复杂，常见场景包括：

- 冷启动
- 热启动
- 前台
- 后台
- 页面切换
- 页面销毁
- 状态恢复

这意味着：

- 请求回来时页面可能已经销毁
- 蓝牙打印进行中时页面可能已经退后台
- 回调回来时未必还能直接更新原页面状态

### 13.2 缓存

缓存不仅是为了“更快”，也是为了：

- 减少网络请求
- 降低 IO 压力
- 减少重复计算
- 改善启动体验
- 降低线程切换和资源消耗

常见缓存类型：

- 接口数据缓存
- 图片缓存
- 蓝牙设备列表缓存
- 草稿缓存
- 用户偏好缓存

## 14. 一份适合当前阶段的总复习结论

### 14.1 关于 JS 异步

- `new Promise()` 里的 executor 是同步执行
- `.then()` 和 `await` 后续逻辑属于微任务
- `setTimeout()` 属于宏任务
- `async/await` 是 `Promise` 的语法糖

### 14.2 关于 Web 视图更新

- 原生 JS：拿到数据后手动改 DOM
- Vue / React：拿到数据后先改状态，再由框架更新界面

### 14.3 关于状态管理

- 小范围使用的状态优先放局部
- 多处共享的状态再考虑全局
- 能算出来的状态不要重复存
- 刷新后还要保留的状态再考虑持久化

### 14.4 关于 RN / uni-app

- 组件状态、生命周期、缓存思路和前端是连通的
- 但客户端比 Web 多了线程、系统 API、本地资源等约束
- UI 更新、JS 逻辑、Native 能力通常不在同一层完成

## 15. 后续复习建议

后面复习时建议按这个顺序回看：

1. 先复习同步 / 微任务 / 宏任务
2. 再看 `Promise`、`async/await`
3. 再看“请求数据 -> 更新状态 -> 界面更新”的链路
4. 再区分局部状态、全局状态、派生状态、持久化状态
5. 最后再结合 RN / uni-app 理解线程、生命周期、系统 API

如果某个知识点又开始混了，就回到最前面的总问题：

`数据从哪里来，存在哪里，谁来更新，更新后谁响应。`
